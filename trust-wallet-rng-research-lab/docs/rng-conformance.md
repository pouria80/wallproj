# RNG Conformance (U2)

## What is verified, and against what
`src/rng_research/mt19937_reference.py` is a from-scratch MT19937 engine.
Its scalar-seeding path (`init_genrand`) + twist + tempering are validated
bit-for-bit against an EXTERNAL oracle: libstdc++ `std::mt19937` compiled with
g++ 12.2.0 (Debian). Oracle provenance (program SHA-256, compiler, fetched
libstdc++ source `random.tcc` SHA-256, vector-file SHA-256) is recorded in the
module docstring and inside `fixtures/references/mt19937_scalar_vectors.txt`.
Tests: `tests/test_mt19937_conformance.py` (9 tests; re-run required offline-safe).

## Verified findings
1. Reference engine == libstdc++ stream for all six seeds {0,1,5489,12345,0xDEADBEEF,0xFFFFFFFF}.
2. CPython `seed(int, version=2)` ≠ libstdc++ `mt19937(int)` streams for the same seed.
   Cause: seeding contract (CPython array-style init vs classic linear recurrence),
   not the MT19937 core. Guarded by
   `test_cpython_seeding_contract_differs_from_libstdcxx`.
3. `temper(1)=4194449`; tempering confirmed bijective on sampled domain.

## UNVERIFIED claims (explicitly)
- Bit-level equivalence of the lab MODEL (`secure_rng.model_random32`, CPython-based)
  to the historical Emscripten/WASM binary: UNVERIFIED. The historical build used
  Emscripten's libc++/libstdc++ combination — which exact standard library shipped
  in the released WASM was not established from primary sources here.
- `seed_array` (init_by_array) path: no external oracle exercised; internally consistent only.
- Runtime behaviour of Emscripten `std::random_device` in affected builds: ledger #6 `needs_more_access`.

## Provenance caveat
Vector file values were generated by executing the recorded oracle program in
this environment (Linux/x86_64, g++ 12.2.0). They are reproducible by anyone
with a C++11 compiler via `fixtures/references/gen_mt.cpp`; different standard
libraries may legitimately differ, which is precisely why the implementation
identity (libstdc++) is pinned above.
